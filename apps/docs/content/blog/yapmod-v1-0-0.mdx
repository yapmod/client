## What is Yapmod, really?

Yapmod is a client modification software that existed since the release of Yapin (formely Yapper) and provide custom plugins and themes. In the very first version of Yapmod, the goal was to build a desktop application that happen to have a client modification software within it. The project grow very rapidly and around 20 people were using it regularly, but the architecture undeneath the project was quite bad. First, because of the desktop application, because everything was built around the idea that we have some sort of host known as a desktop client and we didn't implement any "bridge" at the very start and it was quite bad because it was possible to make it as stable as possible and most importanly, it was not working any other environement then Yapmod Desktop. However, after couple weeks, we've implemented a bridge that allows us to build a web extension.

That bridge was the turning point. Once we separated the client logic from the host environment, everything became possible. The same code could run in a browser extension, a desktop app, or eventually anywhere else. That's when I knew the rewrite was going in the right direction.

## Shelter and why it matters

If you've never heard of [Shelter](https://shelter.uwu.network), it's a Discord client mod that changed how I think about client modification software. The tagline says it all: _"an attempt to prepare for the worst."_

Here's what happened. In 2022, Discord changed their build system and broke every client mod overnight. Overnight, I'm not exaggerating. One day your mod works, the next day it's completely broken because some internal function name changed. Shelter was the response to that problem. Instead of relying on Discord's internal code — which changes constantly — it works with React fibers and DOM observation. It doesn't care what Discord's internals look like. The result? It hasn't broken from a Discord update once in over two years.

That's the philosophy I want for Yapmod. Don't depend on things you can't control. Reuse the host's CSS, use its settings layout, observe the DOM instead of holding references to nodes that will be replaced. Be the mod that keeps working when the app updates. It's not just about being clever — it's about respecting the host application and working with it, not against it.

Shelter also uses Solid for its own UI components — same choice I made. It's small, it doesn't depend on React internals, and running it inside a React app you don't control is actually fine. When you see two projects in the same space making the same choice, it's usually a sign you're on the right path.

## What plugins actually look like

Plugins are why this project exists. Instead of describing the API, let me show you what one looks like:

```tsx
import { Input, Section, SettingRow, SettingsPage } from '@yapmod/ui';

export default function () {
  const storage = yapmod.storage as { greeting?: string };

  return {
    onLoad() {
      yapmod.settings.registerSection({
        id: 'my-plugin',
        label: 'My Plugin',
        render: () => (
          <SettingsPage title="My Plugin">
            <Section label="Settings">
              <SettingRow label="Greeting" hint="What should we say?">
                <Input
                  value={storage.greeting ?? 'Hello!'}
                  onChange={(value) => {
                    storage.greeting = value;
                  }}
                />
              </SettingRow>
            </Section>
          </SettingsPage>
        ),
      });
    },
  };
}
```

That's a complete plugin. A function that returns an object with an `onLoad` hook. You get `yapmod.storage` for persistent data, `yapmod.settings` for a settings panel, `yapmod.log()` for debugging, and a whole UI kit that makes your interface look like it belongs in Yapin. No separate window, no popup — just a new section in the settings.

The storage API is simple: it's just `localStorage` with a reactive proxy. Top-level writes save automatically. If you need nested changes, you call `flushStorage()`. It's predictable, it survives reloads, and if you delete a plugin then reinstall it, your data is still there.

You can install plugins by pasting code, loading a `.js` file, or pointing Yapmod at a remote URL. If a plugin crashes, it doesn't take the rest of the client down. Each plugin runs in isolation, and the error handling makes sure one bad plugin doesn't ruin the experience for everyone else.

### Client-registered plugins

One idea that turned out to be really useful is client-registered plugins. The extension and the desktop app can register their own plugins using the exact same API. They're namespaced with `client:` prefix so they can't collide with community plugins, and regular users don't see them unless they want to.

The web extension's own settings UI is a client-registered plugin:

```tsx
export function createWebExtPlugin(): ClientPlugin {
  return {
    id: 'client:web-ext-config',
    manifest: { name: 'Web Extension Config', author: 'Yapmod' },
    setup(api) {
      api.settings.registerSection({
        id: 'web-ext-config',
        label: 'Extension',
        render: () => (
          <SettingsPage title="Extension">
            <Section label="Release channel">
              <SettingRow label="Channel">
                <Select
                  value={api.storage.channel as string}
                  onChange={(value) => {
                    api.storage.channel = value;
                  }}
                  options={[
                    { value: 'stable', label: 'Stable' },
                    { value: 'prerelease', label: 'Pre-release' },
                  ]}
                />
              </SettingRow>
            </Section>
          </SettingsPage>
        ),
      });
      return { onLoad: () => api.log('Extension config loaded') };
    },
  };
}
```

Same API, same components, same storage. The extension settings look exactly like any other plugin settings because they _are_ plugin settings. The architecture is doing what it was supposed to.

## The web extension

The [web extension](https://github.com/yapmod/web) injects Yapmod into Yapin automatically so you don't have to paste anything into the console. It works on Chrome and Firefox from the same codebase.

Under the hood, it's simpler than you might think: fetch the Yapmod bundle from GitHub releases, inject it into the page, and you're done. But there's one small detail that took me an hour to figure out the first time: Content Security Policy.

Yapin's CSP blocks inline `<script>` tags, so you can't just inject code directly. The solution is Blob URLs — you create a blob from the source code, generate a URL for it, and load it as a regular script:

```js
const blob = new Blob([sourceCode], { type: 'application/javascript' });
const url = URL.createObjectURL(blob);
const script = document.createElement('script');
script.src = url;
document.head.appendChild(script);
```

It's a small detail, but it's the kind of thing that makes or breaks the injection. Once that works, everything else is straightforward.

It's not on the Chrome Web Store yet. You install it by loading the unpacked build from the repo. Store listings will come later when I have time to deal with the review process.

## Design choices that matter

A few decisions that shaped this release:

**One bundle, no eval.** Yapmod is a single file. Yapin's CSP forbids `eval`, so plugins are evaluated through a temporary `<script>` tag. It's a constraint that also keeps things simple — no module bundler for plugins, no complex dependency resolution.

**Light DOM, not Shadow DOM.** Using Yapin's own CSS classes means the settings panel looks native. A shadow root would look like a foreign widget pasted into the page. It's less isolated, but it looks right, and that matters more than perfect isolation.

**One type package.** Plugin authors install `@yapmod/types` and that's it. Everything else is internal. The API surface is small on purpose — less to learn, less to break.

## What's next

The desktop app is next. It will use the same client and the same plugin system — that separation was the whole point of the rewrite. The shell and the mod layer should never break each other.

After that, tests. It's the biggest gap right now, and I know it. A plugin marketplace is also on the radar, but deliberate — plugins are code, and I want to think through the security story before I let people distribute them easily.
