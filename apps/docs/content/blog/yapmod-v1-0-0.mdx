I tagged [v1.0.0](https://github.com/yapmod/client/releases/tag/v1.0.0) today. Everything was rewritten from scratch over the last two weeks — not one file was carried over.

What does "1.0.0" mean? Not that it's finished. It means the foundation is solid enough to build on. The client, the plugin system, the UI kit, the build tool, the types — they work together, and they work well.

## What is Yapmod, really?

Yapmod is a mod that loads into Yapin and gives you themes, plugins, and a settings panel that looks like it belongs there. No separate window, no popup — just a new section in Yapin's settings.

The desktop app isn't part of this release. It's coming next, and it will use the same client and the same plugin system. That separation was the whole point of the rewrite: the shell and the mod layer should never break each other.

## Plugins — the heart of it

Plugins are why this project exists. Let me show you what one looks like instead of describing the API:

```tsx
import { Input, Section, SettingRow, SettingsPage } from '@yapmod/ui';

export default function () {
  const storage = yapmod.storage as { greeting?: string };

  return {
    onLoad() {
      yapmod.settings.registerSection({
        id: 'my-plugin',
        label: 'My Plugin',
        render: () => (
          <SettingsPage title="My Plugin">
            <Section label="Settings">
              <SettingRow label="Greeting" hint="What should we say?">
                <Input
                  value={storage.greeting ?? 'Hello!'}
                  onChange={(value) => {
                    storage.greeting = value;
                  }}
                />
              </SettingRow>
            </Section>
          </SettingsPage>
        ),
      });
    },
  };
}
```

That's it. A function that returns an object with an `onLoad` hook. You get `yapmod.storage` for persistent data, `yapmod.settings` for a settings panel, `yapmod.log()` for debugging, and a whole UI kit that makes your interface look like Yapin.

You can install plugins by pasting code, loading a `.js` file, or pointing Yapmod at a remote URL. If a plugin crashes, it doesn't take the rest of the client down. If you delete it, your data stays — reinstalling brings everything back.

### Client-registered plugins

The extension and the desktop app can register their own plugins using the exact same API. They're namespaced so they can't collide with community plugins, and regular users don't see them unless they want to. It's a small idea that turned out to be really useful.

The web extension's own settings UI is a client-registered plugin:

```tsx
export function createWebExtPlugin(): ClientPlugin {
  return {
    id: 'client:web-ext-config',
    manifest: { name: 'Web Extension Config', author: 'Yapmod' },
    setup(api) {
      api.settings.registerSection({
        id: 'web-ext-config',
        label: 'Extension',
        render: () => (
          <SettingsPage title="Extension">
            <Section label="Release channel">
              <SettingRow label="Channel">
                <Select
                  value={api.storage.channel as string}
                  onChange={(value) => {
                    api.storage.channel = value;
                  }}
                  options={[
                    { value: 'stable', label: 'Stable' },
                    { value: 'prerelease', label: 'Pre-release' },
                  ]}
                />
              </SettingRow>
            </Section>
          </SettingsPage>
        ),
      });
      return { onLoad: () => api.log('Extension config loaded') };
    },
  };
}
```

Same API, same components, same storage. The architecture is doing what it was supposed to.

## The web extension

[Available on GitHub](https://github.com/yapmod/web), the extension injects Yapmod into Yapin automatically so you don't have to paste anything into the console. It works on Chrome and Firefox from the same codebase.

Under the hood it's simple: fetch the Yapmod bundle from GitHub releases, inject it via a Blob URL (Yapin's CSP blocks inline scripts), and you're done. A small detail — Blob URLs instead of inline scripts — but it's the kind of thing that takes an hour to figure out the first time.

It's not on the Chrome Web Store yet. You install it by loading the unpacked build from the repo. Store listings will come later.

## Shelter and why it matters

If you've never heard of [Shelter](https://shelter.uwu.network), it's a Discord client mod with a tagline that says a lot: _"an attempt to prepare for the worst."_

Discord changed their build tool in 2022 and broke every client mod overnight. Shelter was the response. Instead of relying on Discord's internal code — which changes constantly — it works with React fibers and DOM observation. It doesn't care what Discord's internals look like. Result: it hasn't broken from a Discord update once in over two years.

That's the philosophy I want for Yapmod. Don't depend on things you can't control. Reuse the host's CSS, use its settings layout, observe the DOM instead of holding references to nodes that will be replaced. Be the mod that keeps working when the app updates.

Shelter also uses Solid for its own UI components — same choice I made. It's small, it doesn't depend on React internals, and running it inside a React app you don't control is actually fine.

## A few design choices

**One bundle, no eval.** Yapmod is a single file. Yapin's CSP forbids `eval`, so plugins are expressions evaluated through a temporary `<script>` tag. It's a constraint that also keeps things simple.

**Light DOM, not Shadow DOM.** Using Yapin's own CSS classes means the settings panel looks native. It's less isolated, but a shadow root would look like a foreign widget pasted into the page.

**Storage is just localStorage.** Every plugin gets a reactive proxy. Top-level writes save automatically. Nested changes need an explicit `flushStorage()`. Simple, predictable, survives reloads.

**One type package.** Plugin authors install `@yapmod/types` and that's it. Everything else is internal.
