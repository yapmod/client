## The plugin module

A plugin's source is an **expression**, not a statement block. The loader
evaluates it inside a function whose parameter is the plugin API (`yapmod`), so
top-level code can reference `yapmod` directly. If the expression's value is a
function, the loader calls it with the API and uses whatever it returns
(factory form). Otherwise the value is the module object itself.

The module object may export:

- `onLoad()` — runs when the plugin starts. If it throws, the plugin is stopped
  again, switched off and reported.
- `onUnload()` — **optional**. Every disposer-returning API call is
  auto-registered and flushed on stop, so plugins rarely need it.
- `settings` — a legacy settings **modal**: a DOM node, a string of HTML, or a
  function returning either (async functions are supported). When exported, the
  card's gear button appears. This modal is distinct from
  `settings.registerSection()`.

```javascript
{
  onLoad() {
    yapmod.log('hello');
    yapmod.observe('body', (element) => yapmod.log('found', element));
  },
}
```

Nothing above needs an `onUnload`: `observe()` returns a disposer that the
runtime flushes when the plugin stops. Disposers run in reverse registration
order, each isolated in a `try`/`catch`, when the plugin stops or Yapmod
unloads.

In devtools the source appears under `yapmod://<id>` instead of an inline
snippet. Yapin's Content-Security-Policy forbids `eval` and `new Function`, so
evaluation goes through a temporary inline `<script>`.

## The ambient `yapmod` global

TypeScript projects can make the top-level `yapmod` value known to the compiler
by importing the builder's global declaration:

```ts
import type {} from '@yapmod/builder/global';
```

This declares `yapmod` as a `YapmodPluginApi` for the file, so you can write
`yapmod.storage` or `yapmod.ui.showToast()` without importing anything at
runtime.

## Building with `@yapmod/builder`

`@yapmod/builder` compiles plugin TSX and rewrites Solid imports onto the
bundle's shared instance so the result loads straight through the client.

```ts
// build.mjs
import { buildPlugin } from '@yapmod/builder';

await buildPlugin({
  entry: 'src/index.tsx',
  outfile: 'dist/plugin.js',
});
```

`buildPlugin` compiles TS/TSX with `babel-preset-solid` (DOM), rewrites
`solid-js`, `solid-js/web` and `solid-js/store` imports onto `yapmod.solid*`,
bundles with esbuild and writes the loadable expression to `outfile`. A
dependency that still imports `solid-js` fails the build with a clear error.

Paste the built file into _Add Plugin → From Code_ to load it. The builder also
ships a working sample at `packages/builder/examples/hello/index.tsx`; running
`pnpm --filter @yapmod/builder example` builds it through both the builder's
esbuild path and the vite recipe and verifies both load through a mirror of the
client loader.

**Never bundle your own `solid-js`.** Plugins must import from `solid-js`,
`solid-js/web` and `solid-js/store` and let the builder rewrite those imports to
`yapmod.solid*`. The page runs exactly one Solid instance, shared with Yapmod
itself; a second copy would split signal state so plugin components stop
reacting to host updates. `YapmodClient.api` exposes the same shared instances
to embedders.

## Bundler recipe

`yapmodPlugin()` is an unplugin (with adapters such as `yapmodPlugin.vite()` for
vite, rollup, webpack and rspack) that performs the same compile-and-rewrite
pass at build time. Dev servers execute modules outside the loader's `yapmod`
wrapper, so the recipe is for production builds only.

Wrap the finished chunk with `expressionBanner` and `expressionFooter`, and set
the iife global name to `EXPRESSION_GLOBAL_NAME`, so the output stays in the
expression form the loader evaluates. Wrapping must happen after minification
(the banner/footer do this for you) — minifiers prune an uncalled top-level
function expression.

```js
import { fileURLToPath } from 'node:url';

import {
  EXPRESSION_GLOBAL_NAME,
  expressionBanner,
  expressionFooter,
  yapmodPlugin,
} from '@yapmod/builder';

/*
 * The bundler recipe documented in apps/docs/content/docs/plugins/creating.mdx,
 * kept as a working test: the unplugin compiles the sample, and the banner/
 * footer wrap vite's iife output in the expression the loader evaluates.
 */
const root = fileURLToPath(new URL('.', import.meta.url));

export default {
  root,
  plugins: [yapmodPlugin.vite()],
  build: {
    outDir: 'hello/dist',
    emptyOutDir: false,
    lib: {
      entry: 'hello/index.tsx',
      formats: ['iife'],
      name: EXPRESSION_GLOBAL_NAME,
      fileName: () => 'vite-plugin.js',
    },
    rollupOptions: {
      output: { banner: expressionBanner, footer: expressionFooter },
    },
  },
};
```

## Loading

Paste the built expression into _Add Plugin → From Code_, or host it as a
remote plugin folder containing `plugin.json` and `plugin.js` and add it from a
URL. See [Using Plugins](/docs/plugins/using) for the install flow.
