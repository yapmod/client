---
title: Client Plugins
description: How an application embedding Yapmod registers and manages its own plugins.
---

Client plugins are plugins provided by the **application that embeds
Yapmod** instead of imported through the plugin manager. An application
built on Yapmod can ship its own default functionality as plugins, in its
own codebase, and register them at startup — different clients built on the
same foundation each provide their own set.

This is the same idea as Shelter's programmatic plugin registration, as
used by clients such as Dorion.

## Registration

The bundle bootstraps when it is loaded, so the application registers its
plugins right after injection through the public handle:

```html
<script src="/path/to/yapmod-client.js"></script>
<script>
  YapmodClient.registerClientPlugin({
    id: 'client:my-app-presence',
    manifest: {
      name: 'Presence',
      author: 'My App',
      description: 'Shows who is online, provided by My App.',
      version: '1.0.0',
    },
    defaultEnabled: true,
    setup(yapmod) {
      return {
        onLoad() {
          /* start */
        },
        onUnload() {
          /* stop */
        },
        settings: '<p>Options…</p>',
      };
    },
  });
</script>
```

`registerClientPlugin(definition)` validates the definition, records it, and
starts it immediately when it is enabled. It returns `false` when the
definition is rejected; a registered plugin that fails to start is logged
and left disabled.

## Definition

```ts
interface ClientPluginModule {
  onLoad?(): void;
  onUnload?(): void;
  settings?: Node | string | (() => Node | string | Promise<Node | string>);
}

interface ClientPlugin {
  /** Reserved id, always starting with `client:`. */
  id: string;
  /** Metadata shown on the plugin's card. */
  manifest: PluginManifest;
  /** Whether the plugin starts when the user has made no explicit choice. Defaults to `true`. */
  defaultEnabled?: boolean;
  /** Runs synchronously in the host application's own code — nothing is evaluated. */
  setup(api: YapmodPluginApi): ClientPluginModule;
}
```

- The id **must** start with the reserved `client:` prefix, so it can never
  collide with a local plugin id (a slugified name) or a remote id (host
  plus path).
- The manifest must carry a non-empty name; other fields fall back to the
  same defaults the plugin manager uses.
- Malformed or duplicate definitions are **skipped with a `[yapmod]` log**
  instead of throwing, so one bad call never breaks the page.
- `setup` returns the same optional hooks a community plugin exports:
  `onLoad`, `onUnload` and `settings`.

## Same runtime, same lifecycle

Client plugins are not a separate plugin system — only their source and
registration mechanism differ:

- `setup(api)` receives the same `YapmodPluginApi` (`id`, `manifest`,
  `storage`, `flushStorage()`, `onDispose()`, `showSettings()`), and its
  module is activated through the same path as a community plugin.
- Per-plugin data lives in the shared `yapmod.plugins.data.v1`, keyed by
  the `client:` id, so `flushStorage()` behaves identically.
- `stopPlugin`, the settings modal and disposal are reused unchanged:
  unloading Yapmod stops every running client plugin and runs its
  `onUnload` and `onDispose` cleanups alongside community plugins.
- They are never `StoredPlugin` records: not in `yapmod.plugins.v1`, never
  fetched, evaluated, updated or deleted, and excluded from the auto-update
  path.
- The Plugins page only offers a settings button and an enable switch for
  them — no update, edit or delete actions and no safety warning.

## Defaults and user overrides

Enabled state is resolved per plugin:

```text
effective = override ?? definition.defaultEnabled ?? true
```

Explicit choices live in `yapmod.client-plugins.v1` as
`{ "overrides": { "client:<name>": boolean } }`, keyed by the namespaced
id. A host can ship plugins enabled by default without overriding a choice
the user already made, and can ship opt-in plugins with
`defaultEnabled: false`.

## Visibility is separate from activation

The **Show client plugins** toggle in _Yapmod → Settings_ (stored in
`yapmod.settings.v1`) only controls whether the section is rendered on the
Plugins page. It never starts or stops a plugin: hiding a running client
plugin keeps it running, and the section lists plugins whether they are
enabled or disabled.

## Limitations

- Registration is per Yapmod instance. After `YapmodClient.dispose()` and a
  fresh injection, the application registers its plugins again.
- `registerClientPlugin` must be called after the bundle has loaded, since
  it is a method on the handle the bundle creates.
