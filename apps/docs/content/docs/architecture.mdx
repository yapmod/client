## Runtime lifecycle

The client has a predictable lifecycle:

1. The script is loaded and **initializes itself**.
2. `createClient()` creates the runtime in the `ready` state.
3. Features install themselves and register their cleanup with `onDispose()`.
4. `dispose()` runs every registered cleanup: observers, listeners, Solid roots, injected
   elements, and styles are all removed. An error in one cleanup never prevents the rest
   from running.

Initialization is guarded: if the bundle is injected into a page twice, the second
execution returns the existing runtime handle instead of starting a second instance.

A minimal handle is exposed on `globalThis.YapmodClient` with only `version`, `state`, and
`dispose()`. Nothing else about the implementation is global.

## The bundle

`pnpm build` produces one self-contained classic-script file:

```text
apps/client/dist/yapmod-client.js
```

- Executable directly in a browser, as a classic script.
- All runtime dependencies (including SolidJS) are inlined.
- No module loader, no additional chunks, no external CSS file.
- Styles are injected from the JavaScript bundle itself.
- Initializes itself when loaded.

## Layering

- **`@yapmod/core`** knows nothing about SolidJS or Yapin. It is the disposal scope of the
  bundle: features install, register how to undo what they created, and `dispose()` unwinds
  all of it.
- **`@yapmod/ui`** provides the reactive SolidJS components. They render in the light DOM
  and are styled by the package's bundled stylesheet, which mirrors Yapin's own components
  (`.ss2-card`, `.btn`, `.hint`) rule for rule. Its tokens prefer the host's CSS variables
  (`--bg-side`, `--text`, `--accent`, …) and fall back to the same palette outside Yapin, so
  the components follow the host theme without depending on it. Icons are inline SVGs that
  carry their own stroke attributes and need no stylesheet at all.
- **`@yapmod/ui`** also exposes `mountIsolated` for views that genuinely need a hard style
  boundary. The settings integration does not use it: host classes and host CSS lay out the
  page, and only the `yp-` components keep their own stylesheet.
- **`apps/client`** is the only layer that imports both, and the only place that knows
  Yapin's DOM structure. Features live here.

A single SolidJS instance is guaranteed across the workspace (`resolve.dedupe`).

## The settings integration

The first feature registers a Yapmod group of sections in Yapin's native settings modal
(`apps/client/src/features/settings`):

- Sections are grouped the way Yapin groups its own navigation: a group label with one or
  more entries underneath, each entry carrying an inline SVG icon. The first group,
  "Yapmod", holds "Settings", "Plugins" and "Themes".
- Navigation entries are plain `<button>` elements inside `.settings-nav`, so Yapin's own
  `.settings-nav button` rules style them; group labels use `.settings-nav-label`. Yapmod
  adds no nav CSS of its own.
- The host creates the modal lazily, so a single `MutationObserver` on `document.body`
  (child list only) notices it appearing or disappearing. It is the only observer that
  outlives an open modal.
- While the modal is open, two more observers keep the Yapmod nav entries and panels
  attached (React may drop or reorder foreign nodes) and keep the `.active` highlight
  consistent. Both are disconnected when the modal closes or the client is disposed.
- Each Yapmod panel is a light-DOM `.settings-main` sibling of the native panel, so host CSS
  gives it the native padding, width and scrolling. Its content is built from the same
  primitives as Yapin's own settings pages (`h2`, `section-label`, `toggle-row`,
  `toggle-label`, `hint`) and renders with Solid directly into that element.
- Showing and hiding panels is purely structural CSS: a class on the settings root plus
  data attributes on the panels. When React swaps the native panel out, the rules simply
  re-apply to the new element; there is no hidden JavaScript state to resynchronize.
- The page itself is plain host markup: `<h2>`, `.section-label`, `.toggle-row`,
  `.toggle-label` and `.hint`. Only the reactive `Button` keeps `yp-` classes, and its
  stylesheet is written to match the host `.btn` exactly, so the result is visually
  indistinguishable from native settings.

The pattern (install on the client, register one cleanup, keep observers scoped to the
lifetime of what they watch) is the template for future features that integrate with
Yapin's interface.

## Themes

For user-facing instructions, see [Themes](/docs/guide/themes).

The Themes page is the third Yapmod section. It deliberately uses the same layout as the
Plugins page instead of separate local and online tabs:

- A search field and an **Add Theme** button sit above a safety card and a vertical list
  of theme cards. Local and online themes share one list and are sorted by name.
- Adding a theme opens the shared host `.overlay` / `.modal` dialog. A switch toggles
  between a local CSS file and an online CSS URL. Local themes can be uploaded or pasted;
  their metadata block (`@name`, `@author`, `@description`, …) becomes the card title,
  author, description and footer links, and the form fields override it when filled.
- Online themes are direct CSS URLs. The form records whether the URL should apply
  always, only in the light theme, or only in the dark theme. The engine resolves that
  choice against the host's current `data-theme` / `data-look` value and re-resolves it
  when Yapin switches theme.
- Every card has a host `.switch` to enable or disable it and a delete action with a host
  confirmation modal. Uploading a file with the same name replaces the existing local
  theme and keeps its enabled state.
- The safety card carries the performance warning and links to places where themes can be
  found. The add dialog repeats the trust warning and lists the hosts Yapin's CSP allows.

Themes are persisted in one versioned `localStorage` record
(`apps/client/src/features/themes/store.ts`). It stores local theme records, the enabled
local file names, the raw online-theme lines, and the enabled online lines. Older records
without an enabled-online list migrate by enabling every online theme that was already
installed.

The engine (`apps/client/src/features/themes/apply.ts`) owns a single
`<style id="yapmod-theme-styles">` element. Online themes are **fetched and inlined**
rather than linked with `@import`: Yapin enforces a `style-src` that blocks external
stylesheets, while its `connect-src` allows a limited set of hosts such as
`raw.githubusercontent.com`. The engine fetches enabled online CSS through that
allowlist, caches it for the page lifetime, and retries failed URLs after a minute. It
writes the cached online CSS first so enabled local themes can override it, rebuilds the
stylesheet when the theme state or host theme changes, and removes it together with its
observers and media listener on disposal.

## Plugins

For user-facing instructions, see [Plugins](/docs/guide/plugins).

The Plugins page uses a list-based manager:

- A search field and an **Add Plugin** button sit above a vertical list of plugin cards.
  Each card shows the plugin's name, author and description, with settings, update, edit
  and delete actions plus a host `.switch` to enable or disable it.
- Adding or editing opens a host `.overlay` / `.modal` dialog. Remote plugins are installed
  from a folder URL containing `plugin.json` and `plugin.js`.
  Local plugins are pasted or uploaded JavaScript and carry their metadata in the form.
- Remote plugins can refresh themselves when Yapin loads. The update action compares the
  fetched script and manifest and restarts the plugin only when something changed.
- The list is sorted by name and filtered locally across the name, author and description.

Plugins are stored in `localStorage` under `yapmod.plugins.v1`; each plugin's own data is
stored separately under `yapmod.plugins.data.v1`. The runtime
(`apps/client/src/features/plugins/runtime.ts`) evaluates a plugin as an expression that
returns an object with optional `onLoad`, `onUnload` and `settings` members:

```js
({
  onLoad() {
    const element = document.createElement('div');
    element.textContent = 'Hello from a plugin';
    document.body.append(element);
    yapmod.onDispose(() => element.remove());
  },
  settings() {
    return '<p class="hint">Settings can be HTML or a DOM node.</p>';
  },
});
```

The object the runtime passes in exposes:

```ts
interface YapmodPluginApi {
  readonly id: string;
  readonly manifest: {
    name: string;
    author: string;
    description: string;
    version?: string;
    hash?: string;
  };
  readonly storage: Record<string, unknown>;
  flushStorage(): void;
  onDispose(dispose: () => void): void;
  showSettings(): void;
}
```

`settings` can be a DOM node, an HTML string, or a function returning either. `onDispose`
cleanups run when the plugin is disabled, updated, edited or when Yapmod is unloaded.
Disposal stops running plugins without clearing their saved enabled flags, so they start
again on the next load.

Yapin's Content-Security-Policy does not allow `unsafe-eval`, so plugin source is executed
through a short-lived inline `<script>` element instead of `eval` or `new Function`. The
same CSP restricts remote downloads to an allowlist; `raw.githubusercontent.com` is the
practical host for remote plugin folders. The plugin API is Yapmod's own; the remote folder
layout is just a convention.

Plugins run as trusted code in the page's own realm. There is no permission model or
sandbox; the UI carries a warning and the documentation should treat plugin installation
with the same care as running code in the developer console.
