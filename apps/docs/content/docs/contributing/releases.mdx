## Normal releases

[Release Please](https://github.com/googleapis/release-please) maintains one release PR as changes land on `main`. Conventional Commits determine the next versions: `fix:` produces a patch, `feat:` a minor, and a breaking change marked with `!` or `BREAKING CHANGE:` a major.

1. Write release notes in the same PR as your product change, under `## [Unreleased]` in the appropriate changelog. Use a Conventional Commit PR title to select the version bump.
2. Squash-merge the PR. Release Please refreshes the single rolling release PR with the accumulated hand-written notes and version bumps.
3. Review the release PR's versions and notes. Wait for **Checks / check** to pass, then merge it when ready to ship.
4. Release Please creates tags and draft GitHub releases, then dispatches publishing. The client release becomes public only after its bundle is attached; npm releases become public after publishing succeeds.

Merging ordinary PRs only updates the release proposal. Merging the release PR authorizes publishing.

## Writing changelog entries

| Change                     | Changelog to edit                                    |
| -------------------------- | ---------------------------------------------------- |
| Client, core, or shared UI | `CHANGELOG.md`                                       |
| Builder                    | `packages/builder/CHANGELOG.md`                      |
| Public SDK/types           | `packages/types/CHANGELOG.md` **and** `CHANGELOG.md` |

Describe the result for users rather than repeating a commit title. Group concise bullets under `### Added`, `### Changed`, `### Fixed`, or `### Removed`. Include migration instructions for breaking changes and inline links when useful. For example:

```md
## [Unreleased]

### Fixed

- Failed plugin saves now preserve your editor draft and keep the current plugin running.
```

**Checks** requires a changed, nonempty Unreleased section for each affected component when files under its `src/` directory change. Documentation, tests outside `src/`, and tooling-only PRs do not require notes. Add notes for user-visible build or dependency changes too, even though the source-path check cannot detect their impact. An empty Unreleased section does not produce a release for that component.

Automation moves the authored section beneath a version/date heading and leaves an empty Unreleased section for the next batch. It never derives note text from commits. The date is the proposal date in Europe/Paris. Leave version bumps and headings to the release PR.

Correct notes in an ordinary PR against `main`; edits made directly on the release branch will be replaced on refresh. GitHub release notes are read from the versioned changelog at the release PR's merge commit, not its editable description. Keep inline links in entries so they also work in standalone release notes and announcements.

## What gets released

The client, builder, and types have independent versions:

| Component | Version file                    | Tag              | Publishing workflow     |
| --------- | ------------------------------- | ---------------- | ----------------------- |
| Client    | `apps/client/package.json`      | `v1.2.0`         | `release-client.yml`    |
| Builder   | `packages/builder/package.json` | `builder-v1.4.0` | `publish-npm.yml`       |
| Types     | `packages/types/package.json`   | `types-v1.3.0`   | `publish-types-npm.yml` |

The private root package mirrors the client version so Release Please can track the client as the aggregate of its source and shared packages. Its root-path configuration includes core, UI, types, and build dependencies; commits affecting only the docs app or builder are excluded. Release Please updates the root and client package versions together. Core and UI remain bundled source packages and are not published separately.

The client keeps the `yapmod-client.js` asset and `vX.Y.Z` tag format. Only client releases are marked **Latest**, so existing `/releases/latest/download/yapmod-client.js` URLs continue to work. Builder and types GitHub releases are never marked Latest.

The root `CHANGELOG.md` is the canonical client release history. `apps/client/CHANGELOG.md` is a historical archive from the old generator. Package histories retain their existing released entries; all new notes are hand-written.

## Repository setup

Enable **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests**. The release workflow runs a pinned Release Please library with the local `manual-node` strategy in `.github/scripts/manual-changelog.mjs`. It retains Release Please's manifest, rolling branch, labels, version selection, and release lifecycle. The workflows use the built-in `GITHUB_TOKEN`; no personal access token is needed. If branch protection is enabled, require **check** before merging.

GitHub normally suppresses workflow events caused by `GITHUB_TOKEN`. The Release Please workflow explicitly dispatches **Checks** on the release PR branch, and explicitly dispatches **Publish release batch** on `main` with the exact tags from the merged proposal. The batch calls the existing component publishing workflows. Publishing checks out that tag, verifies that its commit belongs to `main`, and checks that the package version matches the release manifest. No publishing workflow commits or pushes version changes.

Keep the existing npm trusted publishers configured for `yapmod/client` and their respective `publish-npm.yml` and `publish-types-npm.yml` filenames. Renaming these files requires changing the npm trusted publisher configuration too. Node 24 supplies a recent npm with OIDC support, and publishing includes provenance.

## Yapin release announcements

**Announce release on Yapin** sends one compact embed for the entire release batch, with a banner and a short excerpt for each changed component. Each section links to its complete release notes on `yapmod.vercel.app/releases/client/<tag>`. The full-notes button opens the site’s Client & SDK release history for combined batches, or the specific release page for a single component. Unchanged components are omitted. At most two buttons remain: the version-specific client download (when included) and full release notes. A single role mention accompanies the embed. Excerpts use the published hand-written notes with category headings and legacy commit hashes removed, and stop at complete lines within 650 characters per component. Duplicate version fields, author labels, footers, and timestamps are omitted. The complete embed stays below Yapin’s 6,000-character limit.

Each announcement generates a 1200 × 480 PNG using the existing Yapmod logo, pink accent, and locally installed Geist fonts. The script uses the docs app’s image renderer and needs no image-generation service or API key. Because Yapin webhooks do not accept file attachments and GitHub release-download URLs fail through its image proxy, the workflow stores banners on the dedicated `release-banners` orphan branch. It uses a commit-pinned `raw.githubusercontent.com` URL that serves the PNG directly. Generated files stay out of `main`, and older announcements retain their original images. The announcement workflow needs `contents: write`; a concurrent asset-branch update fails safely and can be retried.

To render a banner locally, pass a JSON array of GitHub release objects (including `tag_name`) and an output path:

```bash
node apps/docs/scripts/release-banner.mjs releases.json banner.png
```

Set the repository Actions secret `YAPIN_RELEASE_WEBHOOK_URL` to the destination webhook URL. Keep webhook credentials out of the repository. Set the repository Actions variable `YAPIN_RELEASE_ROLE_ID` to the Yapmod role ID. The message pings only that role; user and everyone mentions are disabled. Missing or malformed role IDs fail delivery rather than silently dropping the ping.

**Publish release batch** waits for all requested component publishers to succeed before calling the announcement workflow once. A failed or cancelled publisher prevents the announcement. A batch retry includes all requested components in the message, including those already published by the earlier attempt. If every component was already public, publishing skips the announcement. Individual publishing workflows and manual GitHub publication do not send messages automatically; use the announcement workflow with all desired tags for those cases.

If delivery fails, rerun the failed announcement job. To explicitly resend an announcement, run **Announce release on Yapin** from `main` with space-separated published `tags` (for example, `v1.3.0 builder-v1.4.0 types-v1.3.0`). A new manual run posts another message. Retries within the same Actions run reuse its nonce, so Yapin deduplicates them for ten minutes. After that window, check the channel before retrying because the original request may have succeeded. Delivery failures do not roll back a published release.

## Retry a failed release

For a failed batch, rerun its failed jobs, or run **Publish release batch** from `main` with the same `client`, `builder`, and `types` tags (leave unchanged components empty). This preserves the combined announcement after all publishers succeed. If only the announcement failed, rerun that failed job.

For individual publishing repairs without an automatic announcement, run the relevant publishing workflow **from `main`**, entering the existing tag. For example:

```bash
gh workflow run release-client.yml --ref main -f tag=v1.2.0
gh workflow run publish-npm.yml --ref main -f tag=builder-v1.4.0
gh workflow run publish-types-npm.yml --ref main -f tag=types-v1.3.0
```

Use the actual tag from the failed release, not necessarily the examples above. A batch dispatch with all the proposal’s tags also recovers a failed dispatch after Release Please created its drafts. Re-running Release Please alone does not redispatch already-created releases.

Retries build from the existing tag and never bump a version. Already-published npm versions and existing client assets are skipped; a draft can then be finalized. Registry errors fail the run rather than being mistaken for missing versions. An older client retry does not replace a newer Latest release, and an unpublished older npm version is rejected if publishing it would move npm's `latest` tag backward.

If a release PR's checks were not dispatched, run **Checks** manually with its release branch selected. If release PR creation failed, fix the reported permissions or configuration problem and rerun **Release Please** on `main`.

## Migration baseline

The initial manifest records the already-published versions: client `1.1.0`, builder `1.3.0`, and types `1.2.0`. The bootstrap commit is the existing `v1.1.0` client release, after those package versions were recorded in the repository. This includes the subsequent SDK changes in the first release proposal without replaying the older release history. Release Please uses its tags and manifest to track later releases automatically.

This workflow publishes stable versions. The previous manually requested nightly/prerelease mode is not part of this setup; add a separate prerelease policy before shipping new nightlies.
