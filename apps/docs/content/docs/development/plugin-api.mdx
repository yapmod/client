Every plugin receives a `YapmodPluginApi` object when it starts. This is your gateway to everything Yapmod offers: storage, DOM observation, UI components, settings registration, and more. This page documents every property and method available through that API.

<Callout type="info">
  The built in Plugin API is the recommended way to build plugins. You could technically do
  everything manually by manipulating the DOM yourself, but the API methods are more performant,
  easier to use, and handle cleanup automatically for you.
</Callout>

<Callout type="idea">
  Every property and method documented here is available as a TypeScript type from `@yapmod/types`.
  Install the package and add it to your `tsconfig.json` to get full autocompletion in your editor.
  See the [Type Safety](/docs/development/type-safety) page for setup instructions and a complete
  list of exported types.
</Callout>

## Current call

Use `yapmod.calls` to read or subscribe to the current voice call, set microphone mute or
deafen, and leave. See [Current Call](/docs/development/current-call) for signatures,
error handling, compatibility limits, and testing instructions.

## Local commands

### `api.commands.register(command)`

Register a local slash command with a name, description and callback. For example, typing
`/hello Ada` and pressing **Enter** or **Send** displays a greeting only on your screen:

```typescript
const unregister = yapmod.commands.register({
  name: 'hello',
  description: 'Show a local greeting',
  execute({ args }) {
    yapmod.ui.showToast(`Hello ${args || 'world'}!`);
  },
});

// Optional: remove it early. Plugin shutdown also removes it automatically.
// unregister();
```

The callback receives a `CommandContext`:

| Property | Type          | Meaning                                                                                                                                         |
| -------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `args`   | `string`      | Everything after the command name, trimmed at both ends. Quotes and internal whitespace are preserved; there is no shell-style argument parser. |
| `signal` | `AbortSignal` | Aborted when the registration is removed or its plugin stops. Pass it to cancellable async work.                                                |

Callbacks can return `void` or `Promise<void>`. Each registration runs at most one callback at a
time. A second attempt while it is busy leaves the new draft intact and shows a notice.
A successful dispatch clears the draft before invoking the callback. Callback failures are logged
and shown as an error toast; the command is never sent as a message, and the cleared draft is not
restored. Disposal aborts the signal but cannot forcibly stop a callback that ignores it.

**Names and conflicts:** use 1–32 lowercase ASCII letters, digits, underscores or hyphens,
without the leading `/`. Invocation is case-insensitive. Descriptions must contain 1–200
characters. Invalid definitions and duplicate plugin command names throw synchronously.
`timestamp` is reserved by Yapin. Choose a distinctive prefix such as `myplugin-hello`.
If a native slash command has the same name in a channel, the local suggestion is omitted and
submission is blocked with an explanation. Unregister the local command or disable its plugin
to use the native command. Other native commands and ordinary messages retain their behavior.

**Composer behavior:** suggestions use Yapin's native command menu. **Tab** completes a
suggestion; an exact command runs with **Enter** or **Send**. **Shift+Enter** inserts a newline.
Other modified Enter combinations do not submit local commands, and IME composition does not
execute them. Locked composers and drafts with attachments are rejected without clearing the draft.
Commands belong to the plugin, so they remain available when switching channels and are removed
on disable, reload or client disposal. Calling the returned disposer more than once is safe.

<Callout type="warn">
  Native suggestions currently depend on Yapin's internal composer props. A host update can break
  that integration. If the composer cannot be recognized or its draft cannot be updated, Yapmod
  blocks submission of registered commands and keeps the draft instead of sending it. Suggestions
  refresh on subsequent composer interaction; an already-open menu may briefly show a removed entry.
  Once a command has been unregistered, its name is no longer intercepted.
</Callout>

For older clients, check `yapmod.commands` before registering. `apiVersion` remains `1` because
this is an additive API; the version alone does not identify which optional additions are present.

## Properties

### `api.apiVersion`

**Type:** `1` (readonly)

The current API contract version. You can check this value before using features that are specific to API version 1.

### `api.id`

**Type:** `string` (readonly)

A stable identifier for your plugin. This ID is also used as the key for your plugin's storage in `localStorage`.

### `api.manifest`

**Type:** `PluginManifest` (readonly)

The metadata from your plugin's manifest object. This includes `name`, `author`, `description`, `version`, and `hash`.

### `api.storage`

**Type:** `Record<string, unknown>` (readonly)

This is your plugin's reactive storage, backed by a Solid signal. When you assign a value at the top level, it persists automatically. If you mutate nested values, you need to call `api.flushStorage()` afterward to save the changes.

```typescript
// Top-level assignment persists automatically
api.storage.count = (api.storage.count as number | undefined) ?? 0 + 1;

// Nested mutation requires flushStorage
const data = api.storage.data as { items: string[] } | undefined;
if (data) {
  data.items.push('new item');
  api.flushStorage();
}
```

<Callout type="warn">
  Storage is backed by `localStorage`, which has limited capacity. Storing large amounts of data can
  impact performance. Keep your stored data minimal and only save what you actually need.
</Callout>

### `api.ui`

**Type:** `PluginUi` (readonly)

Everything you need for user interface interactions. This includes toast notifications, modals, CSS injection, and all SolidJS components. See the [UI Helpers](#ui-helpers) section below for details.

### `api.settings`

**Type:** `PluginSettings` (readonly)

Hooks for registering settings sections in the Yapmod settings panel. See the [Settings](#settings) section below.

### `api.solid`

**Type:** `solid-js` (readonly)

The shared SolidJS instance bundled with Yapmod. Use this instead of bundling your own copy of SolidJS. It gives you access to `createSignal`, `createEffect`, `createMemo`, and all other SolidJS primitives.

### `api.solidWeb`

**Type:** `solid-js/web` (readonly)

The shared SolidJS/web instance. Use this for DOM rendering, portals, and other DOM-related helpers.

### `api.solidStore`

**Type:** `solid-js/store` (readonly)

The shared SolidJS/store instance. Use this for `createStore` and `unwrap` when you need fine-grained reactive state management.

## Methods

### `api.flushStorage()`

Writes the current state of `storage` to `localStorage`. You should call this after mutating nested values that would not trigger automatic persistence on their own.

### `api.log(...args)`

Logs a message to the console with a `[yapmod:<id>]` prefix. This makes it easy to filter your plugin's output from everything else in the dev tools console.

```typescript
api.log('Plugin started with config:', config);
```

### `api.observe(selector, onFound)`

**Returns:** Disposer function `() => void`

Watches the page for elements matching the given CSS selector. It calls your `onFound` callback for every matching element that already exists on the page, and for any new elements that appear later. It returns a disposer function you can call to stop the observer.

```typescript
const dispose = api.observe('.message-input', (element) => {
  api.log('Found message input:', element);
  // Modify or interact with the element
});

// Stop observing when no longer needed
dispose();
```

<Callout type="idea">
  The disposer returned by `observe()` runs automatically when your plugin stops, so you do not
  always need to call it manually. But you can also register it with `api.onDispose()` if you want
  explicit control over cleanup.
</Callout>

### `api.onDispose(dispose)`

Registers a cleanup function that runs when your plugin stops or when Yapmod unloads. Use this to clean up event listeners, observers, timers, and any other resources your plugin creates.

```typescript
api.onDispose(() => {
  console.log('Cleaning up plugin resources');
});
```

### `api.showSettings()`

Programmatically opens your plugin's settings modal. This only works if your plugin has registered a settings section. Useful for adding a "Open Settings" button inside your plugin's UI.

## UI Helpers

The `api.ui` object gives you everything you need to interact with the user through the interface.

### `api.ui.showToast(message, kind?)`

Shows a short toast notification that appears over the page and disappears after a few seconds.

- `message` is the text to display
- `kind` is optional and can be `'success'` or `'error'`. It defaults to `'success'`

```typescript
api.ui.showToast('Plugin activated!', 'success');
api.ui.showToast('Something went wrong', 'error');
```

### `api.ui.openModal(options)`

**Returns:** Close function `() => void`

Opens a modal dialog that looks and behaves like Yapin's native modals. You can customize the title, description, content, and footer.

```typescript
const close = api.ui.openModal({
  title: 'My Modal',
  description: 'This is a custom modal',
  content: (close) => <div>Modal content here</div>,
  onClose: () => console.log('Modal closed'),
})

// Close the modal programmatically
close()
```

### `api.ui.injectCss(css)`

**Returns:** Disposer function `() => void`

Injects a `<style>` tag into the page with your custom CSS. Returns a disposer function that removes the style tag when called. The disposer also runs automatically when your plugin stops.

```typescript
const dispose = api.ui.injectCss(`
  .my-custom-class {
    color: red;
  }
`);
```

### `api.ui.registerIcon(name, definition)`

Register reusable inline SVG artwork and receive an opaque `RegisteredIcon` reference.
Use that reference anywhere an icon name is accepted: settings sections, message menu
actions, composer tools, or `<Icon name={icon} />`.

```tsx
const sparkle = api.ui.registerIcon('sparkle', {
  viewBox: '0 0 24 24',
  paths: [{ d: 'M12 3L14 10L21 12L14 14L12 21L10 14L3 12L10 10Z' }],
});

api.settings.registerSection({
  id: 'appearance',
  label: 'Appearance',
  icon: sparkle,
  render: () => <p>Appearance settings</p>,
});
```

Names are local to each plugin setup; registering a duplicate name in that setup throws.
Register icons before registering the UI that uses them. Different plugins and reload
attempts can use the same names without replacing each other's artwork. Definitions are
copied when registered, so later changes to the original object have no effect.

`viewBox` defaults to `0 0 24 24`. Supply one or more `paths`, each containing SVG `d`
data and an optional `fillRule` (`nonzero` or `evenodd`). Icons use `currentColor` by
default. For outline artwork, set `fill: 'none'`, `stroke: 'currentColor'`, and optionally
`strokeWidth`, `strokeLinecap`, and `strokeLinejoin`. Only `currentColor` and `none`
are supported as colors, so icons follow the surrounding theme. No SVG markup or
external URLs are needed. Invalid definitions throw a `TypeError`.

References belong to the current setup and must not be saved in plugin storage. They
expire on unload, including failed setup attempts. Solid icons reactively fall back to
the puzzle icon; newly created DOM icons also use that fallback. Existing plain DOM
icons are snapshots and are removed with their owning menu or settings section.
Register fresh references when the plugin starts again. Built-in names and composer
render callbacks continue to work.

With the builder, `registerIcon` and `Icon` can also be imported from `@yapmod/ui`.
This API requires Yapmod client 1.3.0 or newer; use
`typeof api.ui.registerIcon === 'function'` when supporting older clients.

### SolidJS Components

The `api.ui` object provides SolidJS components that are styled to match Yapin's interface. These include Button, Switch, Input, Textarea, Select, Panel, Hint, Icon, and settings layout components like SettingsPage, Section, SettingRow, SettingText, and Divider.

See the [UI Components](/docs/development/ui-components) guide for the complete reference, including how to access them through the builder (recommended) or manually through `yapmod.ui`.

## Settings

The `api.settings` object lets you add settings sections to the Yapmod settings panel. This is how users configure your plugin.

### `api.settings.registerSection(section)`

**Returns:** Disposer function `() => void`

Adds a new section to the Yapmod settings group. The section is automatically unregistered when your plugin stops.

```tsx
import { createSignal } from 'solid-js';
import { SettingsPage, Section, SettingRow, Switch, Input } from '@yapmod/ui';

const dispose = api.settings.registerSection({
  id: 'my-section',
  label: 'My Plugin Settings',
  icon: 'settings',
  render: () => {
    const [enabled, setEnabled] = createSignal(true);
    const [name, setName] = createSignal('');

    return (
      <SettingsPage title="My Plugin" description="Configure my plugin settings">
        <Section label="General">
          <SettingRow label="Enabled" hint="Toggle the plugin on or off">
            <Switch checked={enabled()} onChange={setEnabled} />
          </SettingRow>

          <SettingRow label="Display name">
            <Input value={name()} onChange={setName} placeholder="Your name" />
          </SettingRow>
        </Section>
      </SettingsPage>
    );
  },
});
```

<Callout type="info">
  Use the settings layout components from `@yapmod/ui` (SettingsPage, Section, SettingRow, and so
  on) to build settings pages that match Yapin's native look and feel. See the [UI
  Components](/docs/development/ui-components) guide for the full component reference.
</Callout>

## Composer blocks

`api.composer.registerBlock(render)` mounts a Solid view once per composer and supplies reactive, read-only composer measurements. [Read the composer block guide](/docs/development/composer-blocks).

## Composer status

### `api.composer.registerStatus(format)`

Add a read-only text indicator to each message composer. The client calls your formatter when the indicator mounts and when the measured length or limit changes. Multiple plugins share a row in registration order. Each composer has its own state, including after Yapin replaces its input.

```ts
export default function () {
  return {
    onLoad() {
      yapmod.composer.registerStatus(({ length, maxLength }) => {
        if (maxLength === null) return String(length);
        return {
          text: `${length} / ${maxLength}`,
          tone: length >= maxLength ? 'warning' : undefined,
        };
      });
    },
  };
}
```

- `length` counts UTF-16 code units, matching textarea `maxlength`. For example, `😀` counts as two.
- `maxLength` is the native limit or `null` when the composer has none. Zero is a valid limit.
- Return a string or an object with `text` and an optional `'warning'` tone. Content is rendered as plain text. Keep the formatter synchronous and free of side effects.
- The returned function removes this registration early. Yapmod also removes its indicators on plugin unload, failed startup or replacement. A newly mounted composer picks up all active registrations.
- Older clients can also report `apiVersion: 1`. Check for `yapmod.composer?.registerStatus` if your plugin supports those clients.

## Composer tools

Use `api.composer.registerTool(tool)` to place an icon button beside the native composer tools. The activation callback receives measurements from the composer containing the button and a function to focus its input. See [Composer tools](/docs/development/composer-tools) for the full contract and responsive layout.
