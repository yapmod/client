When you write plugins in TypeScript, `@yapmod/types` gives you full type safety for the entire plugin API. You get autocompletion, compile time error checking, and precise types for every property, method, and UI component prop.

## How type safety is structured

`@yapmod/types` provides three entry points, each serving a different purpose:

| Entry point                | Purpose                                                   | How to use                                                                    |
| -------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `@yapmod/types`            | Main types: plugin API, client runtime, and UI prop types | Import types directly: `import type { YapmodPluginApi } from '@yapmod/types'` |
| `@yapmod/types/plugin-env` | Ambient `yapmod` global declaration                       | Add to `tsconfig.json` `types` array (see below)                              |
| `@yapmod/types/client-env` | Ambient `globalThis.YapmodClient` declaration             | Add to `tsconfig.json` `types` array for browser extensions                   |

### UI prop types come from one source

UI component prop types like `ButtonProps` and `SwitchProps` are defined in the `@yapmod/ui` components themselves and then re exported from `@yapmod/types`. This means the types can never drift from the actual component signatures, because they are derived directly from the components.

### Ambient declarations are isolated

The `yapmod` global declaration is not automatically picked up when you install `@yapmod/types`. Instead, it lives in a separate entry point called `@yapmod/types/plugin-env` that you explicitly opt into. This prevents the declaration from leaking into projects where `yapmod` does not exist at runtime.

## Installing the types

Add `@yapmod/types` as a development dependency:

```bash
npm install -D @yapmod/types
```

## Configuring TypeScript

### For plugin development (recommended)

Add `@yapmod/types/plugin-env` to the `types` array in your `tsconfig.json`. This loads the `yapmod` global declaration so the variable is typed everywhere in your code:

```json
{
  "compilerOptions": {
    "types": ["@yapmod/types/plugin-env"]
  }
}
```

### For browser extensions or embedders

Add `@yapmod/types/client-env` to get the `globalThis.YapmodClient` type:

```json
{
  "compilerOptions": {
    "types": ["@yapmod/types/client-env"]
  }
}
```

### For type only imports

You can also import types directly without any `types` configuration in your `tsconfig.json`:

```typescript
import type { YapmodPluginApi, PluginManifest } from '@yapmod/types';
```

## What you get

Once configured, the `yapmod` variable is typed as `YapmodPluginApi` everywhere in your plugin source code:

```typescript
// Fully typed, no imports needed
export function onLoad() {
  yapmod.log("plugin loaded");
  yapmod.storage.count = (yapmod.storage.count as number) + 1;
  yapmod.flushStorage();
}

export function settings() {
  return {
    render: () => (
      <yapmod.ui.SettingsPage title="My Plugin">
        <yapmod.ui.Section label="Options">
          {/* ... */}
        </yapmod.ui.Section>
      </yapmod.ui.SettingsPage>
    ),
  };
}
```

Your editor will provide autocompletion for:

- **`yapmod.storage`** for reactive per plugin storage
- **`yapmod.ui.*`** for all UI components like Button, Switch, Input, and Select
- **`yapmod.settings.registerSection()`** for settings panel registration
- **`yapmod.observe()`** for DOM element observation
- **`yapmod.solid`** for shared SolidJS signals and control flow
- **`yapmod.log()`** for prefixed console logging

## All available types

`@yapmod/types` exports **27 types** organized into categories. You can import any of them individually in your plugin code.

### Plugin lifecycle types

These types describe the core plugin contract: how a plugin identifies itself, starts up, and interacts with the Yapmod runtime.

| Type                    | Description                                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `YapmodPluginApi`       | The full API object every started plugin receives. This is the type of the `yapmod` global and the `api` parameter in `start(api)`. |
| `PluginManifest`        | The metadata object for a plugin: `name`, `author`, `description`, `version`, and `hash`.                                           |
| `PluginFunction`        | A function a plugin may export as one of its lifecycle hooks.                                                                       |
| `PluginSettings`        | The settings hooks on the plugin API, including `registerSection()`.                                                                |
| `PluginSettingsSection` | A settings section a plugin registers in the Yapmod settings group, with `id`, `label`, `icon`, and `render`.                       |
| `PluginModalOptions`    | Options accepted by `ui.openModal`: `title`, `description`, `wide`, `content`, `footer`, and `onClose`.                             |
| `ToastKind`             | Message kinds for `ui.showToast`: `'success'` or `'error'`.                                                                         |

```typescript
import type { YapmodPluginApi, PluginManifest, PluginSettingsSection } from '@yapmod/types';

// Type the api parameter explicitly
export function start(api: YapmodPluginApi) {
  api.settings.registerSection({
    id: 'my-section',
    label: 'My Plugin',
    icon: 'settings',
    render: () => <div>Settings content</div>,
  } satisfies PluginSettingsSection);
}
```

### UI component prop types

Every UI component from `@yapmod/ui` has a corresponding prop type you can import. Use these when you need to type component props, create wrapper components, or validate configuration objects.

| Type            | Component  | Description                                                                                                                               |
| --------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `ButtonProps`   | `Button`   | Variants (`default`, `primary`, `accent`, `secondary`, `ghost`, `danger`) and sizes (`medium`, `small`).                                  |
| `SwitchProps`   | `Switch`   | Toggle state: `checked`, `defaultChecked`, `onChange`.                                                                                    |
| `InputProps`    | `Input`    | Single line text: `value`, `defaultValue`, `onChange`.                                                                                    |
| `TextareaProps` | `Textarea` | Multi line text: `value`, `defaultValue`, `onChange`.                                                                                     |
| `SelectProps`   | `Select`   | Dropdown: `options`, `value`, `defaultValue`, `onChange`, `placeholder`.                                                                  |
| `SelectOption`  | —          | A single dropdown option: `value`, `label`, `disabled`.                                                                                   |
| `IconProps`     | `Icon`     | SVG icon: `name`, `size`, `label`, `class`.                                                                                               |
| `IconName`      | —          | Union of built in icon names: `'settings'`, `'puzzle'`, `'trash'`, `'palette'`, `'upload'`, `'refresh'`, `'plus'`, `'pencil'`, `'close'`. |
| `HintProps`     | `Hint`     | Inline hint text (extends native `<span>` attributes).                                                                                    |
| `PanelProps`    | `Panel`    | Card container (extends native `<div>` attributes).                                                                                       |

**Settings layout prop types:**

| Type                | Component      | Description                                                              |
| ------------------- | -------------- | ------------------------------------------------------------------------ |
| `SettingsPageProps` | `SettingsPage` | Top level wrapper: `title`, `description`, `children`.                   |
| `SectionProps`      | `Section`      | Grouped block: `label`, `children`, `spacing` (`'normal'` or `'large'`). |
| `SectionSpacing`    | —              | Spacing variant for Section: `'normal'` or `'large'`.                    |
| `SettingRowProps`   | `SettingRow`   | Single row: `label`, `hint`, `children`.                                 |
| `SettingTextProps`  | `SettingText`  | Read only row: `label`, `hint`, `value`.                                 |

```typescript
import type { SwitchProps, SelectOption } from '@yapmod/types';

// Type a custom wrapper component
function ToggleSetting(props: SwitchProps & { label: string }) {
  return (
    <SettingRow label={props.label}>
      <Switch {...props} />
    </SettingRow>
  );
}

// Type dropdown options
const themeOptions: readonly SelectOption[] = [
  { value: 'default', label: 'Default' },
  { value: 'nord', label: 'Nord' },
];
```

### Shared SolidJS types

These types describe the shared SolidJS instances that the builder injects into your plugin, ensuring all plugins use the same reactive runtime.

| Type          | Description                                                                                                             |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `SharedSolid` | The bundle's single copy of SolidJS, exposing `solid`, `solidWeb`, and `solidStore` module objects.                     |
| `PluginUi`    | The full UI interface: `showToast`, `openModal`, `injectCss`, and all SolidJS components (Button, Switch, Input, etc.). |

```typescript
import type { SharedSolid } from '@yapmod/types';

// Access shared SolidJS with full types
const solid: SharedSolid['solid'] = yapmod.solid;
const { createSignal, createEffect } = solid;
```

### Client runtime types

These types are used by the Yapmod client runtime and embedders, not typically by plugin authors. They are included here for completeness.

| Type           | Description                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| `Client`       | The client runtime created through `createClient()`. Manages lifecycle state and disposal.               |
| `ClientHandle` | The minimal handle exposed on `globalThis.YapmodClient`. Reveals version, state, shared SolidJS, and UI. |
| `ClientState`  | Lifecycle states of the client runtime: `'ready'` or `'disposed'`.                                       |

## The `start(api)` pattern versus the global `yapmod`

There are two ways to access the plugin API, and both are fully typed:

### Using the global `yapmod` (with plugin-env)

When `@yapmod/types/plugin-env` is in your `tsconfig.json` types array, the `yapmod` variable is automatically typed as `YapmodPluginApi` everywhere in your code:

```typescript
// No import needed, yapmod is a typed global
export function onLoad() {
  yapmod.log('loaded');
}
```

### Using the explicit `start(api)` parameter

When using the builder, you can type the `api` parameter explicitly. This is useful for clarity or when the global declaration is not available:

```typescript
import type { YapmodPluginApi } from '@yapmod/types';

export default function (api: YapmodPluginApi) {
  return {
    start(api: YapmodPluginApi) {
      api.log('Plugin started with explicit typing');
    },
  };
}
```

Both approaches give you identical autocompletion and type checking. The global approach is more concise, while the explicit parameter approach makes the dependency clear at each call site.

## How builder import rewriting works with types

When you use `@yapmod/builder`, imports from `solid-js`, `@yapmod/ui`, `solid-js/web`, and `solid-js/store` are rewritten at build time to use the shared runtime instances instead of bundling separate copies.

**Your source code:**

```tsx
import { createSignal } from 'solid-js';
import { Button, Switch } from '@yapmod/ui';
```

**What the builder produces at runtime:**

```js
// Imports are rewritten to use shared instances
const { createSignal } = yapmod.solid;
const { Button, Switch } = yapmod.ui;
```

This rewriting preserves full type safety at compile time because:

1. TypeScript sees your original import statements and resolves types from your local `node_modules`
2. The builder replaces the imports only in the final bundle, never in your source files
3. The shared runtime instances match the types exactly, so what you see at compile time is what runs at runtime

This means you get clean import syntax, full IDE autocompletion, and zero duplicate SolidJS bundles, all at the same time.

## Working with typed storage

The `api.storage` object is typed as `Record<string, unknown>`, which means every value is `unknown` until you cast it. Here are some patterns to work with storage safely:

### Inline type assertion

For simple values, assert the type right where you use it:

```typescript
// Read with a type guard
const count = yapmod.storage.count as number | undefined;
if (count !== undefined) {
  yapmod.storage.count = count + 1;
}
```

### Custom storage interface

For more complex storage shapes, define a custom interface and cast the entire storage object:

```typescript
import type { YapmodPluginApi } from '@yapmod/types';

interface MyPluginStorage {
  count?: number;
  settings?: {
    theme: 'default' | 'nord' | 'gruvbox';
    enabled: boolean;
  };
  history?: string[];
}

export function start(api: YapmodPluginApi) {
  const storage = api.storage as MyPluginStorage;

  // Now you get autocompletion for known keys
  storage.settings = storage.settings ?? { theme: 'default', enabled: true };
  storage.settings.theme = 'nord';
  api.flushStorage();
}
```

### Generic storage helper

If you want reusable type safe access, create a helper function:

```typescript
function getStorage<T>(api: YapmodPluginApi, key: string, fallback: T): T {
  const value = api.storage[key];
  if (value === undefined) {
    api.storage[key] = fallback;
    return fallback;
  }
  return value as T;
}

// Usage
const theme = getStorage(api, 'theme', 'default');
const counters = getStorage(api, 'counters', { clicks: 0, views: 0 });
```

## Automated type contract tests

The `@yapmod/types` package includes automated type contract tests that verify type consistency across packages. These tests use TypeScript's type system to check that UI prop types from `@yapmod/types` match those from `@yapmod/ui` exactly. They also verify that core interfaces like `PluginUi`, `YapmodPluginApi`, and `ClientHandle` maintain their expected structure.

You can run the contract tests with:

```bash
pnpm --filter @yapmod/types test:contracts
```
