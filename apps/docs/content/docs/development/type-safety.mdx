The starter already includes TypeScript configuration. Use this page when setting up an existing project, extracting reusable helpers, or diagnosing a missing type. Types help catch incorrect method names and component props before building; they do not validate persisted data or guarantee that a host integration is available.

## Install and configure the declarations

```bash
pnpm add -D @yapmod/types
```

Add the plugin environment to your existing `tsconfig.json`:

```json
{
  "compilerOptions": {
    "strict": true,
    "jsx": "preserve",
    "jsxImportSource": "solid-js",
    "types": ["@yapmod/types/plugin-env"]
  }
}
```

Merge these options with your project's configuration. `plugin-env` declares the builder-provided `yapmod` variable and the `@yapmod/ui` module. You do not install the UI implementation separately: it is supplied by the client.

| Entry point                | Use it for                                                                             |
| -------------------------- | -------------------------------------------------------------------------------------- |
| `@yapmod/types`            | Explicit type imports such as `YapmodPluginApi`, `PluginCommand`, and component props. |
| `@yapmod/types/plugin-env` | Plugin source that uses `yapmod` and `@yapmod/ui`.                                     |
| `@yapmod/types/client-env` | An extension or embedder that needs `globalThis.YapmodClient`.                         |

A declaration makes a name known to TypeScript; it does not create that value at runtime. `yapmod` is available inside built plugin code, not as a browser-console global.

## Type a reusable integration

Most inline registration callbacks infer their parameter types. Add explicit types when moving a definition into a separate function or file:

```ts
import type { PluginCommand, YapmodPluginApi } from '@yapmod/types';

function registerGreeting(api: YapmodPluginApi) {
  const command = {
    name: 'myplugin-hello',
    description: 'Show a local greeting',
    execute({ args, signal }) {
      if (!signal.aborted) api.ui.showToast(`Hello ${args || 'world'}!`);
    },
  } satisfies PluginCommand;

  return api.commands.register(command);
}

export default function () {
  return {
    onLoad() {
      registerGreeting(yapmod);
    },
  };
}
```

`satisfies` checks the object against the contract while preserving inference. Passing `api` into your own helper makes its dependency explicit. It does not create a new lifecycle convention: the client still calls `onLoad`, not `start(api)`.

## Type component props

Import UI implementations from `@yapmod/ui` and prop types from either its declarations or `@yapmod/types`:

```tsx
import { SettingRow, Switch } from '@yapmod/ui';
import type { SwitchProps } from '@yapmod/types';

function ToggleSetting(props: SwitchProps & { label: string }) {
  return (
    <SettingRow label={props.label}>
      <Switch
        aria-label={props.label}
        checked={props.checked}
        onChange={props.onChange}
        disabled={props.disabled}
      />
    </SettingRow>
  );
}
```

Read props inside the JSX so reactive values stay live. See the [UI reference](/docs/development/ui-components) for control-specific props and previews.

## How builder import rewriting works with types

The builder rewrites imports from `solid-js`, `solid-js/web`, `solid-js/store`, and `@yapmod/ui` to the shared instances on `yapmod`. TypeScript checks the original imports against their declarations; the built file uses the runtime shipped in the client.

This lets you use normal import syntax without bundling a second copy of Solid. A dependency that imports its own Solid runtime is rejected by the builder. See [Core concepts](/docs/development/fundamentals#share-the-runtime) for why sharing matters.

## Working with typed storage

Storage values are `unknown`. Validate them before narrowing their type:

```ts
const saved = yapmod.storage.count;
const count = typeof saved === 'number' && Number.isFinite(saved) ? saved : 0;
yapmod.storage.count = count + 1;
```

`as number` would only silence the compiler; it would not prevent a string or malformed value from being read. For objects, check that the value is a non-null object, validate each field you need, and migrate older schema versions before use. [Settings and storage](/docs/development/settings-and-storage) shows a complete persistent preference.

Top-level writes persist automatically. Call `flushStorage()` after nested mutations, or replace the top-level value to also trigger reactive readers.

## Narrow result unions

Some API results describe more than success or failure. For example, a message that is not in Yapin's cache is different from an unavailable integration:

```ts
async function describeMessage(messageId: string) {
  const result = await yapmod.messages.getLoaded(messageId);
  if (result.status === 'found') {
    return result.message.text ?? 'No text available';
  }
  return result.status === 'not-loaded' ? 'Message is not loaded' : 'Message access is unavailable';
}
```

The `status` check makes `message` available to TypeScript. The request can still reject, so catch failures at the user-facing action boundary. Do not use a cast to skip the unavailable case.

## Check before distributing

The starter runs type checking as part of `pnpm build`. If you invoke the builder directly, run `pnpm exec tsc --noEmit` separately: bundling alone does not check types.

For contributors changing public contracts, run `pnpm --filter @yapmod/types test:contracts` from the client repository. These checks cover agreement between declarations and implementations; a live Yapin test is still needed for host compatibility.
