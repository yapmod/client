---
title: Lifecycle and cleanup
description: Understand when a plugin runs, which resources Yapmod owns, and what you must clean up.
---

A plugin can be enabled, disabled, replaced by a development build, or stopped with the entire client. Treat each start as a fresh instance. This keeps repeated hot reloads from accumulating listeners, timers, or duplicate UI.

## From source to running instance

The client evaluates the built expression to obtain an object, or a function that returns one. It calls `onLoad` to start that instance and `onUnload` when stopping it. The builder supplies `yapmod` to the source function, and the installation supplies the manifest separately.

```ts
export default function () {
  return {
    onLoad() {
      yapmod.log('Counter started');
      yapmod.composer.registerStatus(({ length }) => `${length} characters`);
    },
    onUnload() {
      yapmod.log('Counter stopped');
    },
  };
}
```

Put registrations in `onLoad`. Keep evaluation and the factory free of page changes: Yapmod may evaluate an update before it stops the currently running version. The lifecycle hooks are named `onLoad` and `onUnload`, not `start` and `stop`.

## Know who owns cleanup

| Resource                                                                   | Who removes it?                                                                  |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Composer tools, status indicators, blocks, commands, and settings sections | Yapmod, when the plugin stops.                                                   |
| Styles from `ui.injectCss`, modals, and managed UI locations               | Yapmod, when the plugin stops.                                                   |
| Observers created with `observe` and API subscriptions                     | Yapmod; returned disposers also allow early removal.                             |
| Your own timers, browser listeners, DOM changes, or connections            | Your plugin, through `onDispose`.                                                |
| Saved plugin data                                                          | Persists beyond the running instance, including removal of the installed plugin. |

Register cleanup beside resource creation so it is hard to forget:

```ts
export default function () {
  return {
    onLoad() {
      const handleOnline = () => yapmod.log('Browser is online');
      globalThis.addEventListener('online', handleOnline);
      yapmod.onDispose(() => globalThis.removeEventListener('online', handleOnline));

      const timer = globalThis.setInterval(() => yapmod.log('Still active'), 60_000);
      yapmod.onDispose(() => globalThis.clearInterval(timer));
    },
  };
}
```

`onUnload` is useful for lifecycle-specific work, but you do not need it merely to unregister API resources. Keep cleanup synchronous and independent: releasing a timer should not depend on another cleanup succeeding.

## Return startup work and cancel pending work

If startup must await a subscription, return that promise through an async hook:

```ts
export default function () {
  return {
    async onLoad() {
      await yapmod.context.subscribe((context) => {
        if (context.available) yapmod.log('Current channel', context.channel?.id);
      });
    },
  };
}
```

This lets the update transaction observe startup failure. A detached promise that rejects after `onLoad` returns cannot report its failure as part of that startup. For your own cancellable requests, create an `AbortController`, register `controller.abort()` with `onDispose`, and pass its signal to the request. Cancellation cannot undo work already performed.

## Why the installed file is an expression

Yapin's Content Security Policy blocks `eval` and `new Function`. Yapmod evaluates plugin code using a temporary inline script. The builder produces the required expression, so there is no need to hand-write a loader. Raw TypeScript, JSX, or module imports cannot be uploaded directly.

This is execution inside the page, not a sandbox. API cleanup owns registered resources; it cannot reverse arbitrary global changes or network side effects.

## Check a full stop and restart

Enable the plugin, exercise its feature, disable it, and repeat. Its UI should disappear, its timers and listeners should stop, and enabling again should create one fresh instance. Test navigation too: a successful initial render does not establish behavior after the host replaces its nodes.

## Updating and restoring installed plugins

For an enabled remote plugin, Yapmod evaluates an update before stopping the installed
instance, then waits for the candidate's `onLoad` hook, including a returned promise or
thenable. Its source and manifest are saved only after startup succeeds. If evaluation,
startup, or saving fails, Yapmod retains the installed source and restarts its lifecycle
when necessary. Startup auto-updates use the same transaction.

The plugin card reports **updated**, **current**, **failed**, or **rolled-back**. A failed
fetch or a superseded operation reports failed; rolled-back means the prior source was
retained and its lifecycle recovered if needed. If recovery itself fails, the plugin is
disabled and the outcome is failed. Concurrent update attempts do not replace a pending
candidate. Editing, toggling, pinning, removing, or shutting down invalidates pending work.

Each successful update keeps exactly one previous source and manifest in browser storage.
**Restore previous version** runs the same transaction and pins the restored version. The
version replaced by a restore becomes the single previous version. This history does not
include plugin data, and editing a plugin clears its previous-version snapshot.

**Pin current version** prevents automatic updates. Manual updates remain available and
leave the pin enabled. Unpinning permits startup updates when the plugin's auto-update
setting is enabled. Disabled plugins are skipped during automatic updates; a manual update
or restore saves their source without evaluating it. Their code is first evaluated when
they are enabled, so a successful disabled update does not certify startup.

Rollback covers installed source and API-managed lifecycle resources. Plugins are trusted
page code: arbitrary side effects, network requests, and writes to plugin storage cannot
be undone. Plugins should register cleanups and return their startup promise so Yapmod can
observe failures. A startup promise that never settles leaves that update pending until
another lifecycle action cancels it.
