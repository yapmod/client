This page explains everything that happens from the moment you write plugin code to when it runs in the browser. Understanding this lifecycle will help you build plugins that are reliable and easy to maintain.

## The plugin object

At its core, a Yapmod plugin is simply a JavaScript object that describes what the plugin does. This object has two main parts:

1. **The manifest**. This is metadata about your plugin: its name, author, description, and version.
2. **Lifecycle hooks**. These are functions that run at specific points, like when your plugin starts up or when it is stopped.

Here is a basic example of what a plugin looks like:

```typescript
export default {
  manifest: {
    name: 'My Plugin',
    author: 'Your Name',
    description: 'A simple Yapmod plugin',
    version: '1.0.0',
  },
  start(api) {
    // This runs when the plugin is loaded
    api.log('Plugin started!');
  },
  stop() {
    // This runs when the plugin is disabled or removed
    console.log('Plugin stopped');
  },
};
```

The `manifest` tells Yapmod who you are and what your plugin is called. The `start` function is where your plugin comes to life, and the `stop` function is where you clean up when your plugin is no longer needed.

<Callout type="info">
  Your plugin source code must be an expression that returns the plugin object or a function that
  returns one. It cannot be a statement block. This requirement exists because Yapmod evaluates
  plugins through a temporary inline script tag, which is required by browser Content Security
  Policy.
</Callout>

## The plugin lifecycle

Every plugin goes through four stages from start to finish:

### 1. Loading

When you upload a plugin file to Yapmod, it reads the file content and evaluates it as JavaScript. The result of that evaluation must be a plugin object with at least a `manifest` property. If the evaluation fails or the result is not a valid plugin object, Yapmod will reject the file.

### 2. Starting

If the plugin loads successfully, Yapmod calls your `start()` hook and passes it the `YapmodPluginApi` object. This is where you set up everything your plugin needs: observing DOM elements, registering settings pages, injecting styles, and so on.

<Callout type="info">
  The `api` parameter in `start(api)` is fully typed as `YapmodPluginApi` from `@yapmod/types`. If
  you want to be explicit, you can import the type: `import type {YapmodPluginApi} from
  '@yapmod/types'`. See the [Type Safety](/docs/development/type-safety) page for more details.
</Callout>

### 3. Running

While your plugin is active, it can interact with the page through the API. Your plugin's storage persists across page reloads, so any data you save will still be there when the user refreshes. Any DOM observers you set up will continue running, watching for elements as they appear and disappear.

### 4. Stopping

When your plugin is disabled, removed, or when Yapmod itself unloads, the `stop()` hook runs. This is your opportunity to clean up after yourself. Remove any event listeners you added, dispose of observers, and save any pending state.

<Callout type="warn">
  Always clean up after your plugin. Use `api.onDispose()` to register cleanup functions that run
  automatically when the plugin stops. This ensures you do not leave behind orphaned observers or
  event listeners that continue running after your plugin is gone.
</Callout>

## How Yapmod evaluates your code

Yapmod cannot use `eval()` or `new Function()` to run plugin code. The browser's Content Security Policy (CSP) blocks these methods for security reasons. Instead, Yapmod creates a temporary inline `<script>` tag, injects your plugin source into it, and evaluates it that way.

This has a few important consequences:

- Your plugin source must be valid JavaScript that evaluates to a plugin object
- Your plugin runs in the same context as the rest of the page, so it has full access to the DOM and global browser APIs
- External stylesheets are blocked by CSP, which is why online themes are fetched and inlined into a `<style>` tag instead

## The builder approach

When you use the starter repo, the builder tool takes care of all the complicated parts:

1. You write your plugin in TypeScript with SolidJS support, using normal import syntax
2. The builder compiles and bundles your code into a single JavaScript file
3. The output is a valid plugin file that Yapmod can load without any extra steps

This is why we recommend the starter repo. It handles bundling, compilation, and formatting so you can focus on writing your plugin logic instead of wrestling with build configuration.

## The manual approach

If you choose not to use the builder, you can write your plugin as a plain JavaScript file. The file must return a plugin object that follows the expected structure. But you will need to handle everything yourself:

- Bundling any imports into a single file
- Compiling TypeScript or JSX syntax
- Making sure the output is a valid expression that Yapmod can evaluate

<Callout type="error">
  We do not recommend the manual approach for most users. Without the builder, you lose TypeScript
  support, SolidJS JSX compilation, and all the convenience the build tool provides. Only use this
  approach if you have a specific reason to avoid the starter repo.
</Callout>

## Updating and restoring installed plugins

For an enabled remote plugin, Yapmod evaluates an update before stopping the installed
instance, then waits for the candidate's `onLoad` hook, including a returned promise or
thenable. Its source and manifest are saved only after startup succeeds. If evaluation,
startup, or saving fails, Yapmod retains the installed source and restarts its lifecycle
when necessary. Startup auto-updates use the same transaction.

The plugin card reports **updated**, **current**, **failed**, or **rolled-back**. A failed
fetch or a superseded operation reports failed; rolled-back means the prior source was
retained and its lifecycle recovered if needed. If recovery itself fails, the plugin is
disabled and the outcome is failed. Concurrent update attempts do not replace a pending
candidate. Editing, toggling, pinning, removing, or shutting down invalidates pending work.

Each successful update keeps exactly one previous source and manifest in browser storage.
**Restore previous version** runs the same transaction and pins the restored version. The
version replaced by a restore becomes the single previous version. This history does not
include plugin data, and editing a plugin clears its previous-version snapshot.

**Pin current version** prevents automatic updates. Manual updates remain available and
leave the pin enabled. Unpinning permits startup updates when the plugin's auto-update
setting is enabled. Disabled plugins are skipped during automatic updates; a manual update
or restore saves their source without evaluating it. Their code is first evaluated when
they are enabled, so a successful disabled update does not certify startup.

Rollback covers installed source and API-managed lifecycle resources. Plugins are trusted
page code: arbitrary side effects, network requests, and writes to plugin storage cannot
be undone. Plugins should register cleanups and return their startup promise so Yapmod can
observe failures. A startup promise that never settles leaves that update pending until
another lifecycle action cancels it.
