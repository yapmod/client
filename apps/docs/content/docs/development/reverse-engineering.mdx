---
title: Work with the host DOM
description: Inspect Yapin, handle replaced nodes, and clean up changes outside the managed APIs.
---

Use this approach when [the built-in integrations](/docs/development/choosing-an-api) do not cover your feature. A selector is a dependency on Yapin's current markup. Unlike a composer registration or settings section, it is your responsibility to keep that dependency working after a host update.

## Inspect one interaction at a time

Open Yapin's developer tools, inspect the element you want to extend, and perform the action that reveals it. Repeat after navigating away and back. Look for a narrowly scoped selector that matches the intended elements in both states.

Test candidate selectors in the console with `document.querySelectorAll(selector)`. Check the number and identity of matches, not just whether something exists. Generated classes, translated text, and positional selectors are fragile. Data attributes can help, but their presence does not make them a public contract. In particular, `data-yp-*` markers belong to Yapmod's integration and are not a documented Yapin API.

## Observe current and future nodes

`yapmod.observe(selector, onFound)` visits existing matches and later matches discovered by its observer. It disposes the observer when the plugin stops. It does **not** remove changes made by your callback or turn an old node reference into a reference to its replacement.

This pattern marks nodes without adding duplicate decorations. Replace the example selector with one you have verified against the host:

```ts
export default function () {
  return {
    onLoad() {
      const decorated = new Set<Element>();
      const marker = 'my-plugin-highlight';

      yapmod.ui.injectCss(`
        .my-plugin-highlight {
          outline: 1px solid var(--accent, #ff6b4a);
          outline-offset: -1px;
        }
      `);

      yapmod.onDispose(() => {
        for (const element of decorated) element.classList.remove(marker);
        decorated.clear();
      });

      // Example only: inspect and choose the selector for your actual feature.
      yapmod.observe('.settings-main', (element) => {
        // Release detached nodes rather than retaining every past settings panel.
        for (const previous of decorated) {
          if (!previous.isConnected) {
            previous.classList.remove(marker);
            decorated.delete(previous);
          }
        }
        if (element.classList.contains(marker)) return;
        element.classList.add(marker);
        decorated.add(element);
      });
    },
  };
}
```

Keep callbacks idempotent: running twice should have the same effect as running once. Use a plugin-specific class or marker. Avoid replacing a host container's HTML or changing a controlled input directly; React may overwrite it, and its internal state may no longer match the page.

## Prefer tokens for styling

Read the current host colors in the console:

```js
getComputedStyle(document.documentElement).getPropertyValue('--bg-side');
```

Use `--bg-main`, `--bg-side`, `--text`, `--text-muted`, and `--accent` with fallbacks in plugin CSS. Shared [UI components](/docs/development/ui-components) already follow the host style. The [theme guide](/docs/themes) explains the common tokens.

## Separate unavailable UI from a broken plugin

A selector finding no nodes can simply mean that the user has not opened the relevant view. Leave the feature dormant until it appears. Test opening and closing that view, changing conversations, and disabling the plugin while the view is visible.

Use `yapmod.log` for diagnostics, and show a short error toast when a user-triggered action cannot complete. Do not retry a missing selector continuously or present an error on every DOM mutation.

## Inspect network behavior only when needed

The Network panel can explain a failed request or show when host data becomes available. It does not establish a supported endpoint contract. Before reproducing an internal request, check [app context](/docs/development/app-context), [loaded messages](/docs/development/context-menu-actions), or [current call](/docs/development/current-call) for an existing adapter. Requests made from the page remain subject to Yapin's CSP and the destination's CORS rules.
