To build effective Yapmod plugins, you need to understand how Yapin works under the hood. This page covers the techniques and tools for reverse engineering the Yapin interface so you can find the right elements, data, and patterns to target.

## Why reverse engineering matters

Yapmod plugins run inside the Yapin page, which is a React application. Unlike a public API with documented endpoints, you'll be working with the DOM, CSS selectors, and network requests that Yapin uses internally. Reverse engineering helps you:

- Find the right DOM elements to observe and modify.
- Understand how Yapin structures its data and state.
- Identify stable selectors that won't break when Yapin updates.
- Discover API endpoints and data formats used by the app.

<Callout type="warn">
  Yapin's internal structure may change without notice. Always use the most stable selectors you can
  find, and test your plugin after Yapin updates.
</Callout>

## Inspecting the DOM structure

The first step in reverse engineering is understanding the DOM tree of the Yapin interface.

### Finding elements

Use your browser's **Elements** (or **Inspector**) panel to explore the page:

1. Right-click any element on the Yapin page and select **Inspect**.
2. Navigate the DOM tree to see parent, child, and sibling relationships.
3. Look for patterns in class names, data attributes, and element structure.

### Identifying stable selectors

Not all selectors are created equal. Some are more stable than others:

- **Data attributes** — the most reliable. Yapin uses data attributes like `data-yp-section` and `data-yp-current` for internal state. These are less likely to change.
- **Class names** — moderately reliable. Yapin uses consistent class names like `.ss2-card`, `.settings-main`, `.hint`, `.toggle-row`. However, React may add hash suffixes or change class names in updates.
- **CSS variables** — Yapin uses CSS custom properties like `--bg-side`, `--text`, `--accent`. These are stable for styling purposes.
- **Element text content** — fragile. Text can change with localization or UI updates.
- **DOM position** — very fragile. Never rely on element position in the DOM tree.

<Callout type="idea">
  When targeting elements, prefer data attributes first, then class names, and avoid relying on DOM
  structure or text content.
</Callout>

## Understanding React rendering

Yapin is built with React, which means the DOM is managed by React's virtual DOM. This has important implications:

### DOM nodes can be replaced

React may remove and re-create DOM nodes during re-renders. If you hold a direct reference to a DOM element, it may become stale after a re-render.

**Solution:** Use `api.observe()` which handles this automatically with `MutationObserver`. It will call your callback for both existing elements and new elements that appear later.

### React component patterns

Look for these patterns in the DOM:

- **Fragment wrappers** — React often wraps content in `<div>` fragments with no meaningful class names.
- **Key attributes** — React adds `data-reactroot` or similar attributes to mark component boundaries.
- **Event handlers** — React attaches event handlers to elements. You can see these in the Elements panel as `onclick`, `onmouseover`, etc.

## Analyzing network traffic

The **Network** panel in your browser dev tools is invaluable for understanding how Yapin communicates with its backend.

### Finding API endpoints

1. Open the Network panel and filter by **Fetch/XHR** to see API requests.
2. Look at the request URL, method, headers, and payload.
3. Note the response format (usually JSON) and structure.

### Understanding data flow

By observing network traffic, you can:

- See what data Yapin fetches when you perform actions.
- Understand the request/response format for API calls.
- Identify authentication tokens and headers.
- Discover endpoints that might be useful for your plugin.

<Callout type="info">
  You don't need to replicate Yapin's API calls in your plugin. The plugin API gives you access to
  the data and UI you need. Network analysis is mainly for understanding how the app works.
</Callout>

## Using the Console for exploration

The browser **Console** panel is your best friend for quick exploration:

### Querying elements

```javascript
// Find elements by selector
document.querySelector('.settings-main');
document.querySelectorAll('.ss2-card');

// Check if an element exists
document.querySelector('[data-yp-section]') !== null;
```

### Inspecting objects

```javascript
// Inspect a DOM element
inspect(document.querySelector('.settings-main'));

// Check CSS variables
getComputedStyle(document.documentElement).getPropertyValue('--bg-side');
```

### Testing selectors

Before writing your plugin, test your selectors in the console to make sure they match the elements you expect:

```javascript
// Test a selector
const elements = document.querySelectorAll('.message-input');
console.log(`Found ${elements.length} elements`);
elements.forEach((el, i) => console.log(`${i}:`, el));
```

## Finding CSS patterns

Yapin uses a consistent set of CSS classes and variables. Understanding these helps you style your plugin's UI to match the host interface.

### Common Yapin classes

- `.ss2-card` — card-like containers
- `.settings-main` — main settings panel content
- `.hint` — inline hint text
- `.toggle-row` — settings toggle rows
- `.input` — text input fields
- `.switch` — toggle switches
- `.overlay` — modal overlays
- `.modal` — modal dialog containers
- `.btn` — button styles

### CSS variables

Yapin uses CSS custom properties for theming:

- `--bg-side` — sidebar background color
- `--text` — primary text color
- `--accent` — accent color
- `--bg-primary` — primary background
- `--bg-secondary` — secondary background

Use these variables in your plugin's CSS to ensure your UI adapts to the current theme.

## Practical tips

- **Start small** — begin by inspecting one element and understanding its structure before moving to the next.
- **Use the Elements panel** — it's your primary tool for understanding the DOM.
- **Test selectors in the console** — before committing to a selector in your plugin, verify it works.
- **Look for data attributes** — they are the most stable way to target elements.
- **Understand React patterns** — knowing how React renders helps you predict how the DOM will change.
- **Check the network** — understanding API calls helps you understand the data flow.
- **Be prepared for changes** — Yapin may update its interface, so design your plugin to be resilient.
