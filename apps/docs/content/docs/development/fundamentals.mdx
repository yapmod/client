You can start with basic JavaScript: functions, objects, imports, and promises. TypeScript helps your editor explain the plugin API, but you do not need to learn every type before [building the counter](/docs/development/first-plugin).

## Source code and the installed file are different

Your entry point is a TypeScript module. The builder resolves imports, compiles JSX, and wraps its output as a JavaScript expression the client can load. An `export default` statement belongs in your source; upload the resulting `plugin.js` to Yapmod.

The builder supplies the `yapmod` variable inside the plugin. It is scoped to that plugin's API and is not a browser-console global. `YapmodClient` is the separate client handle used to check the installation or dispose the whole client.

## Solid renders plugin UI

Yapin uses React, but Yapmod's plugin components use **Solid**. The JSX looks similar; the update model is different. Solid runs a component to establish reactive work, then updates the relevant parts when the values it reads change.

```tsx
import { createSignal } from 'solid-js';
import { Button } from '@yapmod/ui';

function CounterButton() {
  const [count, setCount] = createSignal(0);
  return <Button onClick={() => setCount(count() + 1)}>Clicked {count()} times</Button>;
}
```

`count` is a getter. Calling `count()` inside JSX lets Solid track it. Calling it once outside the reactive view and keeping that number would give you a snapshot instead.

This example's count lives only as long as the mounted view. Use [plugin storage](/docs/development/settings-and-storage) when a value should survive disabling the plugin or reloading Yapin.

## Share the runtime

Import Solid primitives and `@yapmod/ui` components normally in builder source. The builder rewrites those imports to the runtime already supplied by Yapmod. Bundling a second copy of Solid can separate your signals from the components reading them, so the builder rejects dependencies that try to bring their own Solid runtime.

## The host can replace its DOM

Navigation, opening settings, and other React updates can replace nodes you inspected earlier. A reference to an old node does not become a reference to the replacement. Prefer [managed integrations](/docs/development/choosing-an-api); use observers when you need to handle host nodes directly.

## Async work needs a lifecycle

Return a promise from `onLoad` when startup depends on asynchronous work. Register cleanup for resources you own, and cancel work that should not continue after disable. [Lifecycle and cleanup](/docs/development/how-plugins-work) shows this pattern and explains what Yapmod already disposes for you.
